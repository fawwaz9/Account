Implementation Plan
- Start with the base features for Calender and Tasks so we can work on features with a foundation.

Clear the ground first
- Fix the two deposit bugs before anything touches the ledger again. group_id already
  means both "transfer pair" and "deposit split"; recurring transactions would make it
  mean a third thing on top of a bug.
- Wire vite.config.ts and tsconfig.json. Everything below ships blind until the build
  type-checks and Tailwind actually generates.

Foundation
- events table plus a recurrence rule (freq, interval, byday, until/count). Materialise
  occurrences on read for the window asked for; never store them.
- Class times as the first consumer: a course generates lecture/lab/discussion blocks.
  Proves the engine before two other features depend on it.
- tasks table: title, due date, estimated minutes, course_id, tags, done/archived.
  Anything with a date renders on the calendar.
- Due dates on grades, then auto-create a task from any dated grade and close it when
  the score lands.
- Course flags in one migration: no_final, transfer_credit, archived. Tiny change,
  unblocks the Attention panel, credits completed and the average rules at once.

Build on it
- Midterm and final event kinds so the calendar can theme those cards differently.
- Recurring transactions once group_id is untangled. Same engine as class times.
- One tokenizer: course code, date word, duration, amount, score/max. Quick capture
  uses it first.
- Omnibox is that tokenizer plus a module router. Nearly free once it exists.
- course_id on transactions unlocks every Grades x Budget idea in a single step.
- Syllabus parser becomes the default add-course path, manual behind a button.

Cheap wins, read-only
- Free blocks, crunch radar, week load, term timeline, best/worst band, blind spots.
  All derived from data already stored; no new tables, no writes.
- Safe-to-spend and sinking funds, after recurring transactions exist to read from.
- PDF export: a print stylesheet and window.print(). No dependency.
- Read-only offline: cache the shell, stale-while-revalidate the GETs.

Collaboration, by invite
- No shared ownership. The invitee gets their own row; every existing query keeps
  filtering by user_id and nothing else changes. This is how real calendar invites
  work.
- invitations table: source_id, kind (event/task), from_user, to_user, status
  (pending/accepted/declined).
- On accept, copy the event or task into the invitee's own table with an origin_id
  pointing back at the original.
- Organiser edits propagate to accepted copies; organiser deletes mark them cancelled
  rather than vanishing them.
- Address people by email. Return the same response whether or not the address has an
  account, so the endpoint cannot be used to enumerate users.
- An invites inbox, and the only cross-user write in the whole app is one narrow
  insert. Easy to audit.
- Decide once: assigning a task means the other person owns it; sharing means you both
  track it. They are different rows.
