        Midterm and final event kinds, themed as exams rather than class blocks.
        Course flags: no_final, transfer_credit, archived, with the credit and
          average rules each flag changes.
        Recurring transactions in all four kinds, on the same engine as class times.
        Repeating tasks -- the engine's third consumer, so all three now run on it.
        Estimated minutes, tags, course-code categorisation, check-to-archive.
        One tokenizer: course code, date word, duration, amount, score/max.
        Quick capture on the Tasks page, and the omnibox on top of the same parser.
        A week view on the calendar: 24 hours, overlapping classes side by side.
        The account page in two columns, with the target bar dividing them.
        Bonus as a real category: its weight sits outside the 100 the course is
          marked out of, and its marks are added on top, banked against the whole
          course rather than the graded slice.
        Bonus on screen: the course badge, "+2.50" in the strip rather than a
          fraction, a gold row for a grade above its own max, and forms that stay
          silent until a score actually goes over.
        Best/worst band: where a course can still finish, projected per unmarked
          item rather than per category, hidden once nothing is outstanding.
        Archived courses marked and hideable, the flag finally read.
        A final's card distinct from a midterm's.
        Fractional scores and weights, which the columns always allowed -- the
          inputs defaulted to step="1" and refused anything else.
        course_id on transactions, so a textbook can say which course it was for.
          Tagged by dropdown, by the description, or through the omnibox.
        Pay Tuition: a rate times the term's credits, plus fees belonging to no

        What a course cost, on the course page: its gross tuition share plus

Implementation Plan

The engine now has all three consumers it was written for, the tokenizer has two,
and the Grades UI debts are cleared. What is left splits into one piece of
plumbing that unblocks a whole section, a set of derivations that need no new
tables at all, and the things that genuinely need new storage.

What is left of Grades x Budget -- next
- The plumbing is in. A dropped course's dollar figure and a term budget that
  knows its own dates are now each a query rather than a feature.
- The dropped-course figure wants one decision first: refunds are income, and a
  course_id is expense-only, so a refund is currently attributed to nothing. That
  was deliberate -- it keeps one rule for what a labelled transaction means -- but
  it means cost per course reads gross rather than net, and a drop with a refund
  is exactly where that shows.

Cheap wins, read-only
- Free blocks, crunch radar, week load, term timeline, category blind spots,
  term retrospective. All derived from data already stored: no new tables, no
  writes, and each one is a service function plus a chart.
- The band that shipped is the pattern for the rest of them: project_average in
  grade_service.py shows the shape, including the rule that a projection must
  agree with the live number at the ends or it is a second opinion.
- Free blocks is the closest to free of them: the week view already lays the day
  out against the clock, so the gaps are arithmetic on data it holds.
- Safe-to-spend and sinking funds. /recurring/upcoming already returns the
  commitments, so safe-to-spend is a subtraction.
- Subscription audit reads the ledger for repeats that have no standing
  instruction behind them -- which is only possible now that standing
  instructions exist to compare against.
- PDF export: a print stylesheet and window.print(). No dependency.
- Read-only offline: cache the shell, stale-while-revalidate the GETs.

Needs new storage, so later
- Reminders that notify, as opposed to tasks that wait.
- Snooze with a reason, kept, so the pattern is readable after a term.
- Reimbursement state, and who/when on Money Lent.
- Grade-to-effort log.
- At-risk-first task sorting needs no storage, but it does need the dashboard's
  below-target rule reachable from the task list, so it belongs with these.
- What-if sandbox. Read-only in effect, but it needs the whole term recomputed
  from hypothetical inputs, so it wants the averaging code reachable without a
  session first.

Syllabus parser
- Deliberately late. It proposes categories, weights and due dates for review,
  which means it depends on due dates, category weights and the course flags all
  being settled -- they are -- and on the tokenizer for dates, which now exists.
- Default path when adding a course, manual behind a button. When editing, manual
  is the default and the parser sits under the grid.

Worth knowing before picking anything up
- The shipped block sits on two branches: `repeating-tasks` (pushed) and
  `bonus-and-grades-clarity` on top of it. main is a strict ancestor of both, so
  they merge without conflicts -- unlike the grades-branch merge, where every
  reported conflict turned out to be phantom (identical trees under different
  SHAs).
- It carries a migration: one nullable tasks.recurring_id and the recurring_tasks
  table. Additive and idempotent like the rest, but back up data/app.db first.
- gh is not installed and no token is exported. git push works because the
  credential sits in the macOS keychain, but opening a PR means the browser, or
  installing gh first.
- 261 backend tests. The frontend has none: the week view's overlap maths was
  checked with a one-off esbuild harness, not by anything that runs on its own.
  Vitest would slot in beside Vite cheaply if that starts to bite.
- Repeat rules live in five columns shared by events, standing payments and
  repeating tasks, read and written through Calendar/utils/rule_columns.py.
- Bonus is the one category whose weight is not part of the denominator. Anything
  that sums category_weights wants scoring_weight() from Grades/utils/enums.py
  instead; six sites already special-case Final and route the bonus exclusion
  through is_additive() rather than repeating the check.
- Scores, weights and target grades are floats everywhere. A number input for any
  of them needs step="any" -- without it the browser defaults to step="1" and
  rejects half marks, which is how that went unnoticed for so long.
- A tuition payment writes exactly one ledger row, never one per course. What a
  course cost is a Grades answer -- credits times the term's per-credit rate,
  gross -- and is not meant to tie out against the ledger, which records the net
  of one payment covering a whole term.
- Per-credit rates are additive across a term's payments, so two instalments mean
  entering half the rate twice. credits_counted is stored rather than recomputed
  because it is what the bill was for.
- resolve_course lives in Grades/services/course_lookup.py now, with three
  callers: quick capture, the omnibox, and tagging an expense.
- FastAPI matches routes in declaration order, so any literal path under
  /courses/ must be declared above /courses/{course_id} or it is parsed as an id.
- A repeat materialises differently per module, and the differences are the
  point: class times never become rows, payments become rows only once they have
  happened, tasks become rows a little way ahead so each can be ticked off.

Collaboration, by invite
- No shared ownership. The invitee gets their own row; every existing query keeps
  filtering by user_id and nothing else changes. This is how real calendar invites
  work.
- invitations table: source_id, kind (event/task), from_user, to_user, status
  (pending/accepted/declined).
- On accept, copy the event or task into the invitee's own table with an origin_id
  pointing back at the original.
- Organiser edits propagate to accepted copies; organiser deletes mark them cancelled
  rather than vanishing them.
- Address people by email. Return the same response whether or not the address has an
  account, so the endpoint cannot be used to enumerate users.
- An invites inbox, and the only cross-user write in the whole app is one narrow
  insert. Easy to audit.
- Decide once: assigning a task means the other person owns it; sharing means you both
  track it. They are different rows.
