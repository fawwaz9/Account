        Due dates on grades, and the choice of what a date means: a task that
          closes when the score lands, or a calendar block with nothing to tick off.
        Midterm and final event kinds, themed as exams rather than class blocks.
        Course flags: no_final, transfer_credit, archived, with the credit and
          average rules each flag changes.
        Recurring transactions in all four kinds, on the same engine as class times.
        Repeating tasks -- the engine's third consumer, so all three now run on it.
        Estimated minutes, tags, course-code categorisation, check-to-archive.
        One tokenizer: course code, date word, duration, amount, score/max.
        Quick capture on the Tasks page, and the omnibox on top of the same parser.
        A week view on the calendar: 24 hours, overlapping classes side by side.
        The account page in two columns, with the target bar dividing them.


Tasks:  Shows midterms and exams coming up in the next 30 days.
        Reminders, as opposed to tasks: something that notifies rather than waits.
        At-risk first: tasks belonging to courses below target sort to the top of the list.

        Bonus marks in the UI. The backend already allows a category total to 200%

        Best/worst case band on every course: what you get if you ace everything left, and if you bomb it.
        Cheapest path to a target: which remaining item moves the average most per hour spent.
        Category blind spots across all courses: you may be losing marks in labs everywhere, not in one class.
        Term retrospective when a term closes: what moved, what slipped, what you predicted vs got.
        Syllabus paste: drop the text in, get categories, weights and due dates proposed for review.

        When editing courses the manual is the default but syllabus parser will be available under the manual grid.

Calendar:
        Free-block finder: the gaps between your classes, ranked by length, so study time gets scheduled instead of hoped for.
        Crunch radar: a density strip across the term showing which weeks stack up. Visible in September, not the night before.
        Reading break and term boundaries pulled from course start/end dates, blocked out automatically.

Budget:

Grades x Budget (nothing else does this):

Quality of Life:

Implementation Plan

The engine now has all three consumers it was written for, and the tokenizer has
two. What is left splits into one piece of plumbing that unblocks a whole
section, a set of derivations that need no new tables at all, a short list of UI
debts, and the things that genuinely need new storage.

course_id on transactions -- next
- One nullable column, and every Grades x Budget idea becomes a query rather than
  a feature: cost per course, materials by course code, the dollar figure beside
  a dropped course, the term budget that already knows the term dates.
- First, because two of the cheap wins below want it and because it is the last
  bit of plumbing anything is waiting on.

Cheap wins, read-only
- Free blocks, crunch radar, week load, term timeline, best/worst band, category
  blind spots, term retrospective. All derived from data already stored: no new
  tables, no writes, and each one is a service function plus a chart.
- Free blocks is the closest to free of them: the week view already lays the day
  out against the clock, so the gaps are arithmetic on data it holds.
- Safe-to-spend and sinking funds. /recurring/upcoming already returns the
  commitments, so safe-to-spend is a subtraction.
- Subscription audit reads the ledger for repeats that have no standing
  instruction behind them -- which is only possible now that standing
  instructions exist to compare against.
- PDF export: a print stylesheet and window.print(). No dependency.
- Read-only offline: cache the shell, stale-while-revalidate the GETs.

Small UI debts, worth clearing in one pass
- Archived courses marked and hideable in the course list.
- Bonus marks surfaced: say that a category may exceed 100% and show when a
  course is carrying bonus, rather than only permitting it silently.
- A final's card distinct from a midterm's. Both currently share one exam style.

Needs new storage, so later
- Reminders that notify, as opposed to tasks that wait.
- Snooze with a reason, kept, so the pattern is readable after a term.
- Reimbursement state, and who/when on Money Lent.
- Grade-to-effort log.
- At-risk-first task sorting needs no storage, but it does need the dashboard's
  below-target rule reachable from the task list, so it belongs with these.
- What-if sandbox. Read-only in effect, but it needs the whole term recomputed
  from hypothetical inputs, so it wants the averaging code reachable without a
  session first.

Syllabus parser
- Deliberately late. It proposes categories, weights and due dates for review,
  which means it depends on due dates, category weights and the course flags all
  being settled -- they are -- and on the tokenizer for dates, which now exists.
- Default path when adding a course, manual behind a button. When editing, manual
  is the default and the parser sits under the grid.

Worth knowing before picking anything up
- Everything in the shipped block above sits on the `repeating-tasks` branch,
  pushed to origin. main is a strict ancestor of it, so it merges without
  conflicts -- unlike the grades-branch merge, where every reported conflict
  turned out to be phantom (identical trees under different SHAs).
- It carries a migration: one nullable tasks.recurring_id and the recurring_tasks
  table. Additive and idempotent like the rest, but back up data/app.db first.
- gh is not installed and no token is exported. git push works because the
  credential sits in the macOS keychain, but opening a PR means the browser, or
  installing gh first.
- 224 backend tests. The frontend has none: the week view's overlap maths was
  checked with a one-off esbuild harness, not by anything that runs on its own.
  Vitest would slot in beside Vite cheaply if that starts to bite.
- Repeat rules live in five columns shared by events, standing payments and
  repeating tasks, read and written through Calendar/utils/rule_columns.py.
- A repeat materialises differently per module, and the differences are the
  point: class times never become rows, payments become rows only once they have
  happened, tasks become rows a little way ahead so each can be ticked off.

Collaboration, by invite
- No shared ownership. The invitee gets their own row; every existing query keeps
  filtering by user_id and nothing else changes. This is how real calendar invites
  work.
- invitations table: source_id, kind (event/task), from_user, to_user, status
  (pending/accepted/declined).
- On accept, copy the event or task into the invitee's own table with an origin_id
  pointing back at the original.
- Organiser edits propagate to accepted copies; organiser deletes mark them cancelled
  rather than vanishing them.
- Address people by email. Return the same response whether or not the address has an
  account, so the endpoint cannot be used to enumerate users.
- An invites inbox, and the only cross-user write in the whole app is one narrow
  insert. Easy to audit.
- Decide once: assigning a task means the other person owns it; sharing means you both
  track it. They are different rows.
